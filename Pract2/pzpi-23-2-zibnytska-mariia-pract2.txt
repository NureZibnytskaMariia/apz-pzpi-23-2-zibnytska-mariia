3 ОПИС ВИКОНАНОЇ РОБОТИ 
3.1 Загальні відомості про систему
Назва системи: Moodle (акронім від Modular Object-Oriented Dynamic Learning Environment).
Розробник: Moodle розробляється та підтримується компанією Moodle Pty Ltd, відомою як Moodle HQ. 
Засновник: Мартін Дугіамас.
Moodle — це система управління навчанням (LMS), розроблена для того, щоб забезпечити викладачів, адміністраторів та учнів єдиною надійною, безпечною та інтегрованою системою для створення персоналізованого навчального середовища.
Область застосування: Від індивідуальних онлайн-курсів до масштабних інфраструктур великих університетів.
Користувачі: Система базується на рольовій моделі. Ключові ролі – Адміністратор, Викладач, Студент. Користувачі об'єднуються в межах Курсів.
Основні функції та структура контенту:
* Ресурси: Статичний контент (PDF-файли, HTML-сторінки, посилання).
* Активності (Activities): Інструменти для взаємодії та оцінювання (форуми, тести, вікі).
* Логічна структура: Можливість групування матеріалів за темами або за календарним принципом (тижнями).


3.2 Архітектурний стиль системи
Проведений аналіз архітектурної організації платформи дистанційного навчання Moodle свідчить про те, що вона не є реалізацією одного архітектурного шаблону. Дослідження внутрішньої структури системи, механізмів обробки запитів та способів збереження даних дозволяє класифікувати Moodle як гібридну програмну систему.
У структурі Moodle чітко виділяються три взаємопов’язані архітектурні стилі, кожен з яких відповідає за свій логічний рівень функціонування:
* Шарова архітектура (Layered / N-Tier Architecture) – визначає базову інженерну організацію системи, забезпечуючи чіткий розподіл між вихідним кодом додатка, реляційною базою даних та ізольованим сховищем файлів користувачів.
* Клієнт-серверна архітектура (Client-Server Architecture) – регламентує мережеву взаємодію між кінцевими користувачами (через веб-браузери) та обчислювальними ресурсами сервера, визначаючи специфіку диспетчеризації HTTP-запитів.
* Мікроядерна або плагінна архітектура (Microkernel / Plug-in Architecture) – формує рівень бізнес-логіки та є ключовим інструментом масштабування функціональних можливостей платформи через строгу типізацію незалежних модулів розширення.
Нижче наведено детальний розбір теоретичних засад кожного з виявлених архітектурних стилів.
        
        3.2.1 Шарова архітектура (Layered / N-Tier Architecture)
Шарова архітектура базується на принципі розмежування повноважень (Separation of Concerns) шляхом декомпозиції системи на горизонтальні рівні (layers). Кожен шар виконує строго визначену групу функцій і виступає абстракцією для вищого рівня. Базове правило архітектури – ієрархічна односпрямованість: запити рухаються зверху вниз.
У класичному виконанні складна програмна система розподіляється на чотири рівні:
* Шар представлення (Presentation Layer) – відповідає за взаємодію з користувачем, приймання вхідних даних (HTTP-запитів) та візуалізацію інтерфейсу.
* Шар бізнес-логіки (Business Logic / Application Layer) – містить ядро системи, правила й алгоритми предметної області, координуючи виконання процесів.
* Шар доступу до даних (Data Access Layer / Repository) – інкапсулює низькорівневі SQL-запити та роботу зі сховищами, трансформуючи записи у високорівневі структури.
* Доменний шар (Entity Layer) – описує фундаментальні сутності бізнес-моделі, які залишаються незмінними при зміні технічної реалізації бази даних чи інтерфейсу.
Залежно від строгості дотримання меж виділяють два підходи до проектування:
* Строге шарування (Strict Layering) – компонент певного рівня звертається виключно до шару безпосередньо під ним. Це максимізує незалежність та полегшує тестування, але створює надлишковий транзитний код для простих операцій.
* Послаблене шарування (Relaxed Layering) – дозволяє вищим рівням оминати суміжні шари (наприклад, звертатися до бази даних напряму з контролера представлення). Це прискорює розробку, проте підвищує зв'язність (tight coupling) компонентів.
Аналіз технічної архітектури платформи Moodle показав використання послабленого шарування. Головним обмеженням у Moodle є автономність плагінів на макрорівні, тоді як усередині самих модулів жорсткі межі між представленням, логікою та доступом до даних свідомо розмиті задля зниження накладних витрат і підвищення швидкодії системи.
Оцінюючи баланс характеристик даного архітектурного стилю, варто відзначити, що його головні переваги полягають у високій модульності коду, простоті розуміння структури розробниками, можливості паралельної роботи над різними рівнями системи та незалежному горизонтальному масштабуванні окремих фізичних шарів. Проте ефект від цих переваг може нівелюватися суттєвими недоліками під час еволюції великих проєктів. Зокрема, проявляється проблема “горизонтального зрізу”, коли впровадження будь-якої нової функції вимагає одночасної модифікації всіх рівнів від інтерфейсу до таблиць бази даних. Крім того, за відсутності автоматизованого контролю виникає ефект розмивання меж, через який розробники починають викликати низькорівневі методи безпосередньо з представлення, що поступово перетворює систему на важкопідтримуваний моноліт.
Шарова архітектура демонструє найвищу ефективність у системах із відносно стабільними бізнес-правилами, де домінують операції збереження та зчитування даних (CRUD), а також у додатках з вираженою орієнтацією на роботу з централізованими сховищами даних.


3.2.2 Клієнт-серверна архітектура (Client-Server Architecture)
        Клієнт-серверна архітектура є мережевою моделлю розподілу навантаження, яка регламентує взаємодію між клієнтами (ініціаторами запитів) та серверами (постачальниками послуг і ресурсів). Вона визначає правила комунікації та оптимізації обчислень у вебпроєктах.
Базова схема розподілу функцій у цій моделі містить три компоненти:
* Клієнт (Client) – веббраузер або застосунок, що забезпечує інтерфейс користувача, формує запити та візуалізує отримані результати.
* Сервер (Server) – обчислювальна система, яка очікує на запити, виконує бізнес-логіку, керує доступом до бази даних і повертає відповіді.
* Комунікаційна мережа (Network) – середовище передачі даних, де взаємодія координується за допомогою прикладних протоколів (HTTP/HTTPS, WebSockets).
Головними перевагами клієнт-серверного стилю є централізоване керування ресурсами, безпека даних на стороні сервера, чітке розділення інтерфейсних та обчислювальних задач, а також можливість незалежного масштабування серверних потужностей.
Водночас моделі притаманні суттєві обмеження. Основним ризиком є наявність єдиної точки відмови (Single Point of Failure), коли збій центрального сервера чи бази даних повністю блокує роботу системи. Крім того, функціонування додатка критично залежить від пропускної здатності мережі та затримок (latency), а обслуговування великої кількості одночасних клієнтських сесій вимагає значних серверних ресурсів, що змушує впроваджувати складні механізми балансування трафіку та кешування.


3.2.3 Мікроядерна (плагінна) архітектура (Microkernel / Plug-in Architecture)
Мікроядерна архітектура є розширюваним шаблоном проектування, що передбачає розділення системи на два типи компонентів: мінімальне базове ядро (Host Application) та незалежні, ізольовані модулі розширення (Plugins / Add-ons). Це дозволяє динамічно нарощувати функціональність системи під специфічні вимоги без модифікації та перекомпіляції її вихідного коду.
Функціонування плагінної архітектури забезпечується взаємодією трьох базових елементів:


* Хост-застосунок (Ядро) – центральний комплекс, який керує життєвим циклом системи, забезпечує базові функції та платформу для запуску розширень.
* Модуль розширення (Плагін) – автономний компонент, який залежить від ядра і функціонує в його середовищі, додаючи нові бізнес-функції або інтерфейсні елементи.
* Прикладний інтерфейс програмування (API) – набір правил та інтерфейсів, які ядро відкриває для розширень. Комунікація відбувається виключно через цей зафіксований API-шар.
Життєвий цикл та інтеграція плагінів складається з кількох послідовних етапів: ідентифікація та реєстрація (динамічне сканування директорій та зчитування метаданих), ініціалізація (підключення до точок розширення – hooks), виконання (активація коду у відповідь на тригери) та керування життєвим циклом (безпечне оновлення чи деактивація модуля).
Головні переваги мікроядерного стилю полягають у високій гнучкості конфігурації платформи, стабільності ядра (збій у плагіні не зупиняє хост-застосунок) та ефективності розробки завдяки можливості залучення сторонніх команд розробників.
Проте архітектурі притаманні й специфічні недоліки. Плагіни є потенційним вектором кібератак, що вимагає впровадження строгого контролю прав доступу. Одночасна інсталяція великої кількості модулів створює ризик міжмодульних конфліктів та надмірного використання ресурсів. Крім того, еволюція хост-застосунку ускладнюється через необхідність тривалої підтримки зворотної сумісності версій API.
Мікроядерна архітектура є оптимальним вибором для великих тиражованих програмних продуктів (систем керування контентом CMS, середовищ розробки IDE, графічних та аудіоредакторів), де неможливо заздалегідь передбачити всі потенційні сценарії використання продукту кінцевим споживачем.
3.3 Основні компоненти системи
Практична реалізація гібридного архітектурного стилю системи Moodle базується на чіткому розподілі функціональних обов’язків між її внутрішніми компонентами та зовнішніми сервісами. На відміну від стандартних монолітних рішень, де межі між підсистемами є суто умовними, у Moodle кожен компонент ізольований на рівні файлової структури, конфігураційних файлів та спеціалізованих інтерфейсів прикладного програмування (API).
        3.3.1 Інтерфейс користувача
        Підсистема інтерфейсу користувача Moodle реалізована за принципом серверного вебпредставлення (Server-Side Rendering). Кінцеві сторінки повністю утворюються на стороні сервера і передаються клієнту у вигляді готового HTML-коду, CSS-стилів та клієнтських скриптів.
Програмно-архітектурна організація цього рівня базується на кількох підходах:
* Об’єктна абстракція виведення даних. В межах життєвого циклу HTTP-запиту ядро ініціалізує два глобальні об’єкти, які ізолюють бізнес-логіку від прямого генерування HTML-тегів. Об'єкт сторінки ($PAGE) виступає головним контейнером метаданих поточної сторінки (URL, заголовки, блоки). Основний рендерер ядра ($OUTPUT) відповідає за виведення стандартних візуальних елементів за допомогою уніфікованих методів (генерація шапки $OUTPUT->header(), контейнерів вмісту та підвалу сайту). Механізм виділених рендерерів плагінів (Plugin Renderers) дозволяє графічним темам перевизначати (override) вигляд елементів без втручання в логіку плагіна.
* Платформна дизайн-система. Працює на базі фреймворку Bootstrap із використанням власних дизайн-токенів (Design Tokens) – централізованих змінних для оформлення (кольори, відступи, шрифти). Це уніфікує інтерфейс, економить час на підтримку коду (maintainability) та захищає систему від хаосу в оформленні.
* Стандартизація та ергономіка вебформ. Проектування форм на базі бібліотеки HTML QuickForm підпорядковується суворим правилам: обмеження щільності інформації (до 5–6 полів на секцію), автоматичне згортання секцій (крім першої та обов'язкових) та лаконічне іменування розділів (General, Appearance, Availability). Архітектура вимагає уникати приховування розширених налаштувань, забезпечуючи передбачуваність інтерфейсу.
* Підсистема інтернаціоналізації. Забезпечує багатомовність за допомогою функції get_string(). Переклади винесені у статичні мовні пакети (Language Packs) у вигляді асоціативних PHP-масивів, де ключі прив'язані до унікального імені плагіна (Frankenstyle). Локалізація підтримує ієрархічне успадкування мов, динамічно адаптується під налаштування користувача чи курсу та дозволяє підставляти змінні в шаблони текстів через маркер {$a}.
3.3.2 Серверна частина
Серверна частина (Backend) системи Moodle функціонує за принципом сервіс-орієнтованого моноліту (Service-Oriented Monolithic Architecture). Увесь базовий функціонал платформи зосереджений у її ядрі (Moodle Core), яке надає розробникам плагінів набір низькорівневих сервісів через строго регламентовані Core APIs.
Завдяки чіткому розділенню системних обов’язків, ядро платформи ізолює критично важливі сервіси від логіки конкретних модулів, забезпечуючи високу стабільність та безпеку обробки даних на серверному рівні.
Hooks API (Подієво-орієнтована взаємодія плагінів).
Починаючи з актуальних версій, Moodle здійснив архітектурний перехід від застарілих кастомних коллбеків (lib.php callbacks) до сучасної подієвої моделі на основі міжнародного стандарту PSR-14 (Event Dispatcher). Це дозволяє кастомізувати поведінку ядра (наприклад, перевірку політики паролів або валідацію форм) через локальні плагіни без прямого втручання в код ядра.
Відповідно до стандарту PSR-14, архітектура Hooks API у Moodle реалізує такі ролі:
* Hook (Event): Об’єкт ( arbitrary PHP class), який інкапсулює в собі дані події (наприклад, \core_form\hook\before_form_validation). Усі класи хуків оголошуються як final і використовують атрибути PHP (наприклад, #[attribute\label]) для самодокументування.
* Hook Emitter / Dispatcher: Місце в коді, де ядро викликає менеджер хуків. Для диспетчеризації Moodle використовує сучасний механізм впровадження залежностей (Dependency Injection) через контейнер: \core\di::get(\core\hook\manager::class)->dispatch($hook);.
* Hook Callback (Listener): Окремі методи плагінів, що реєструються у файлі db/hooks.php із визначеним пріоритетом виконання (за замовчуванням 100, чим вище число – тим раніше виконається код).
Архітектура підтримує Stoppable Events (через інтерфейс StoppableEventInterface). Це дозволяє одному з плагінів виконати метод $hook->stop(), що миттєво припиняє подальше розповсюдження події (Propagation) іншим слухачам, захищаючи систему від перевизначення критичних бізнес-даних.
Lock API (Контроль паралелізму та синхронізація процесів).
У високонавантажених або кластерних системах виникає проблема одночасного доступу кількох процесів до одного ресурсу, наприклад, паралельний запуск важких фонових завдань cron або генерація звітів. Для запобігання ситуаціям "гонки даних" (race conditions) backend-частина реалізує шар Lock API.
Lock API оперує концепцією фабрик блокувань (lock_factory), конфігурація яких задається на рівні файлу config.php (наприклад, використання Redis для розподілених систем: $CFG->lock_factory = ‘\local_redis\lock\redis_lock_factory’).
Життєвий цикл блокування ресурсу на сервері є строго детермінованим:
1. Визначення простору імен компонента (наприклад, mod_assign_download_submissions).
2. Генерація унікального ключа ресурсу (resource key), який часто включає ID користувача.
3. Спроба захоплення блокування з таймаутом (get_lock($resource, $timeout)). Якщо ресурс зайнятий – процес очікує або викидає виключення locktimeout.
4. Обов’язкове вивільнення ресурсу ($lock->release()) у блоці обробки помилок, що гарантує відсутність «мертвих блокувань» (deadlocks) у системі.
Життєвий цикл обробки серверного запиту (Request Pipeline)
Кожен HTTP-запит, який надходить від браузера користувача до серверної частини Moodle, проходить крізь уніфікований конвеєр обробки, що складається з таких послідовних етапів:
1. Точка входу та ініціалізація (Bootstrapping): Запит клієнта потрапляє на конкретний контролер (наприклад, view.php або index.php), який першим ділом підключає кореневий файл конфігурації config.php. На цьому етапі розгортається глобальне серверне середовище, запускаються Core APIs, підключається DI-контейнер та створюється об'єкт роботи з базою даних $DB.
2. Автентифікація користувача: Система викликає обов'язкову функцію require_login(), яка перевіряє поточну сесію користувача, валідує cookie-файли та переконується, що користувач успішно пройшов розпізнавання в системі.
3. Контекстна перевірка безпеки: Замість лінійних ролей Moodle обчислює права у межах ієрархії контекстів (Сайт -> Категорія -> Курс -> Модуль). Механізм ядра перевіряє, чи має поточна сесія специфічний дозвіл (Capability) на виконання запитуваної дії саме в поточному бізнес-контексті.
4. Обробка логіки та перехоплення подій: Backend запускає виконання коду конкретного плагіна. У цей момент через Hooks API (на базі стандарту PSR-14) ядро дозволяє стороннім модулям перехопити керування або модифікувати дані без прямого втручання в основні файли системи.
5. Взаємодія з шаром даних: Бізнес-код плагіна виконує необхідні маніпуляції з інформацією, надсилаючи безпечні запити до СУБД через об'єктно-орієнтовані методи Data Manipulation API ($DB), що виключає появу SQL-ін’єкцій.
6. Рендеринг відповіді: Після завершення обчислень backend передає зібрані дані на шар представлення. За допомогою Output API система генерує фінальну HTML-сторінку або JSON-відповідь і повертає її клієнту.


3.3.3 Рівень бізнес-логіки
Рівень бізнес-логіки Moodle реалізовано за принципом модульного моноліту, де прикладна логіка відокремлена від інфраструктури ядра й задекларована у lib/components.json у вигляді двох типів компонентів. Перший – підсистеми ядра (Core Subsystems, як-от аналітика чи кешування), які жорстко вбудовані в платформу й не можуть бути вимкнені. Другий – типи плагінів (Plugin Types, наприклад, модулі активностей mod, блоки block або системи аутентифікації auth), що слугують точками розширення для динамічного адаптування системи під потреби навчання.
Взаємодія плагінів із ядром регламентується суворими стандартами іменування та життєвого циклу. За стандартом Frankenstyle-іменування машинне ім'я плагіна має складатися з його типу та назви в нижньому регістрі латиниці. Воно валідується методом core_component:: is_valid_plugin_name() за допомогою регулярного виразу /^[a-z](?:[a-z0-9_](?!__))*[a-z0-9]+$/, а некоректні назви сервер ігнорує. У разі застарівання модуля запускається триетапний процес виведення з експлуатації (Deprecation Process): спочатку плагін виключається з комунікації ядра, а згодом – повністю блокує оновлення сайту до моменту фізичного видалення його бізнес-коду з файлової системи.
Для демонстрації взаємодії компонентів на бізнес-рівні розглянемо структуру стандартного модуля сторінок-лекцій mod/page. Його архітектура базується на взаємодії трьох обов’язкових файлів. Файл version.php декларує версію модуля та його Frankenstyle-ідентифікатор mod_page. Файл lib.php виступає внутрішньою бібліотекою функцій бізнес-логіки для ядра. Файл view.php функціонує як контролер і головна точка входу для обробки запитів.

Детальний аналіз реального вихідного коду дозволяє виділити такі архітектурні закономірності взаємодії шарів:
* Безпечна валідація вхідних даних: замість прямого звернення до суперглобальних масивів бізнес-рівень використовує функцію ядра optional_param(). Вона автоматично очищує дані та приводить їх до строгого типу PARAM_INT, запобігаючи ін’єкціям та XSS-атакам на етапі ініціалізації запиту.
* Динамічне розділення сутностей: код демонструє розділення архітектури на загальний модуль курсу (coursemodule) та конкретний екземпляр плагіна (page). Запит обробляється двома альтернативними шляхами (через параметр $p або $id), забезпечуючи гнучке відновлення зв’язків між БД, структурою курсу та логікою плагіна за допомогою DAL-методу $DB->get_record().
* Гранулярна перевірка прав доступу: функція require_course_login() ізолює сесію в межах конкретного навчального курсу, а метод require_capability() виконує точкову перевірку – чи має поточний користувач право mod/page:view саме в обчисленому контексті цього модуля сторінки ($context).
* Формування представлення (Output API): бізнес-код не містить прямої HTML-розмітки. Виведення системного заголовка сторінки ($OUTPUT->header()), підвалу сайту ($OUTPUT->footer()) та фільтрація внутрішнього контенту лекції (format_text) виконуються через глобальні об’єкти представлення ядра, забезпечуючи уніфікований вигляд інтерфейсу платформи.
        3.3.4 Рівень зберігання даних
Рівень зберігання даних Moodle реалізовано у вигляді уніфікованої абстракції, яка ізолює бізнес-логіку від специфіки конкретних РСУБД (PostgreSQL, MariaDB, MySQL, Oracle, MS SQL). Замість важких сторонніх бібліотек сучасна архітектура платформи використовує власну полегшену обгортку (thin wrapper) навколо стандартних драйверів PHP, яка поділяється на два інтерфейси: DML API та DDL API.
Інтерфейс Data Manipulation API (DML) відповідає за обробку даних за допомогою глобального об'єкта класу moodle_database (змінна $DB). Виклик високорівневих методів (наприклад, $DB->get_record()) автоматично транслюється у безпечний SQL-запит. Під час написання кастомного SQL через $DB->get_records_sql() архітектура вимагає дотримання кросплатформних правил: назви таблиць обов'язково обгортаються у фігурні дужки (наприклад, {course}) для автоматичного підставляння префікса mdl_, динамічні значення передаються виключно через плейсхолдери (:categoryid або ?) для захисту від SQL-ін'єкцій, а для специфічних операцій (як-от конкатенація) використовуються сумісні функції ядра на кшталт $DB->sql_concat().
Інтерфейс Data Definition API (DDL) керує структурою бази даних. У Moodle заборонені прямі інструкції CREATE TABLE чи ALTER TABLE. Структура сутностей описується в нейтральному форматі всередині XML-файлів (наприклад, mod/page/db/install.xml). Під час інсталяції або оновлення інструмент XMLDB парсить ці файли та генерує точний SQL-код під поточну СУБД. Зміна структури між версіями описується у файлі upgrade.php через менеджер блокувань структури $dbman = $DB->get_manager(); за допомогою об'єктних методів (table_exists(), add_field(), change_field_type()).
З історичних причин база даних Moodle не використовує фізичні зовнішні ключі на рівні самої СУБД. Це спрощує міграцію та роботу на різних рушіях баз даних, проте переносить усю відповідальність за контроль цілісності даних із плечей СУБД на програмну логіку підсистем ядра платформи.
3.3.5 Допоміжні сервіси
Допоміжні сервіси (Core APIs) формують низькорівневий інфраструктурний фундамент Moodle. Вони надають плагінам уніфіковані інструменти для життєдіяльності та асинхронної взаємодії.
Центральним сервісом автоматизації є Task API, який керує запуском фонових процесів для запобігання тайм-аутам веб-сервера. Він розділяє завдання на планові (Scheduled tasks), що діють за розкладом адміністратора, та ситуативні (Adhoc tasks), які створюються розробниками для відкладених операцій (наприклад, відправки email). Підсистема має вбудовану відмовоустійливість: у разі помилки завдання перезапускається за прогресивним алгоритмом (retry algorithm) з інтервалом від 1 хвилини до 24 годин. Метод clear_static_caches() при цьому запобігає витоку оперативної пам’яті.
Фундаментальна підсистема File API повністю ізолює файлову систему сервера через концепцію безпечних зон (File Areas). Кожен завантажений файл ідентифікується в базі за чотирма параметрами: contextid, Frankenstyle-ім’я компонента, filearea (наприклад, intro) та itemid. Прямий доступ до диску заблоковано. Всі маніпуляції здійснюються через менеджер get_file_storage(), а віддача контенту користувачу маршрутизується через шлюз pluginfile.php, який перед рендерингом викликає обов’язковий колбек плагіна для перевірки прав доступу.
Для оптимізації швидкодії використовується універсальний кеш Cache API (MUC). Він розділяє оперативні дані на три режими: MODE_APPLICATION (глобальний кеш), MODE_SESSION (в межах сесії) та MODE_REQUEST (статичний кеш на час одного HTTP-запиту). Конфігурація зон описується у файлах db/caches.php, а механізм requirelockingbeforewrite захищає систему від “кеш-колапсів” (cache stampedes) під час пікових навантажень.
Слабозв’язану комунікацію забезпечує Hooks API, побудований на сучасному стандарті PSR-14. Менеджер хуків через Dependency Injection (\core\di::get) здійснює диспетчеризацію об’єктів-хуків (dispatch($hook)) серед зареєстрованих у файлах db/hooks.php слухачів. Це дозволяє динамічно модифікувати логіку платформи без ризику порушити цілісність коду ядра.


3.4 Взаємодія компонентів
Для комплексного аналізу динаміки функціонування платформи дистанційного навчання Moodle та визначення логіки інтеграції плагінів розроблено дві взаємопов’язані UML-моделі: статичну діаграму компонентів та динамічну діаграма послідовності. Разом вони описують архітектурні патерни, потоки даних, протоколи взаємодії та механізми забезпечення безпеки системи.
Взаємодія між структурними рівнями архітектури чітко розмежована за типами запитів та протоколами передачі даних. Веб-браузер користувача ініціює прямі синхронні запити до скриптів відображення плагінів за протоколом HTTP/HTTPS, отримуючи у відповідь динамічний HTML-код, стилі та клієнтські сценарії. Водночас мобільний додаток Moodle Mobile App та зовнішні інтелектуальні сервіси взаємодіють із платформою виключно через шлюз веб-служб за допомогою RESTful API, обмінюючись структурованими даними у форматі JSON. Внутрішньосистемні потоки даних між серверними компонентами повністю ізольовані й відбуваються на рівні викликів PHP API. Компоненти плагінів позбавлені прямого доступу до файлової системи чи глобального кешу, тому будь-яка операція делегується відповідним інфраструктурним підсистемам ядра, таким як File API, Cache API (MUC), Task API та подієво-орієнтований інтерфейс Hooks API стандарту PSR-14.
Статична структура та декомпозиція системи за шаблоном проектування “Ідеальний дизайн плагіна” (Ideal Design Pattern) детально представлена на компонентній діаграмі (рис. 1).
  

Рисунок 1 – Діаграма компонентів системи Moodle
На цій діаграмі чітко виділено три логічні рівні. Рівень клієнта (Client Layer) містить зовнішні автономні сутності: браузер, мобільний додаток та сервіси ШІ. Наступний шар – ядро Moodle та підсистеми (Moodle Core & Subsystems) – виступає фундаментом моноліту, який через набір Subsystem APIs управляє спільними ресурсами та системними бібліотеками. Рівень розширень (Plugins Layer) демонструє внутрішню ізоляцію самого плагіна, де зовнішній шлюз Webservice API та проміжний контролер External API Layer обгортають Component API. Саме в Component API зосереджена вся бізнес-логіка та UI-компоненти плагіна, які взаємодіють із ядром системи. На найнижчому рівні розширень перебуває Low Level API, що виконує безпечні CRUD-операції з базою даних через глобальний об’єкт $DB і сповіщає ядро про зміни через диспетчеризацію подій.
Динаміку поведінки системи в часі та покроковий життєвий цикл обробки запиту ілюструє діаграма послідовності (рис. 2).
  

Рисунок 2 – Діаграма послідовності виконання запиту користувача
Як показано на схемі, процес обробки починається з етапу ініціалізації середовища (Bootstrapping), коли HTTP-запити від браузера до плагіна викликають конфігураційні файли ядра, підключають базу даних $DB та активують глобальні змінні. Після цього підсистема автентифікації синхронно перевіряє сесійні куки користувача у браузері. На етапі обчислення прав доступу сервіс Access API зчитує з бази даних призначені ролі, агрегує дозволи та повертає плагіну статус дозволу на виконання. Отримавши доступ, скрипт плагіна безпечно очищує вхідні параметри, здійснює синхронний запис бізнес-події в аудит-лог бази даних і переходить до етапу генерації виводу. Формування інтерфейсу реалізується через об'єкти $PAGE та $OUTPUT у вигляді потокової передачі даних. Рушій виводу послідовно підвантажує активну тему, блоки сайту та віддає клієнту спочатку шапку сторінки, потім очищений від XSS-вразливостей центральний контент плагіна, а наприкінці – підвал сайту разом із клієнтськими JavaScript-тегами. Така модель взаємодії гарантує жорсткий контроль безпеки, оскільки кожен крок плагіна контролюється відповідними Core APIs.
3.5 Масштабованість та надійність
Для забезпечення стабільного функціонування платформи в умовах пікових навантажень, таких як одночасне складання тестів великою кількістю студентів, архітектура системи передбачає комплексне застосування механізмів масштабованості, відмовостійкості та контейнеризації. Оскільки ядро Moodle спроєктоване як моноліт, його горизонтальне масштабування реалізується за допомогою рознесення критичних шарів інфраструктури (веб-серверів, бази даних та сховища файлів) на окремі вузли під керуванням балансувальника навантаження (рис. 3).
  

Рисунок 3 – Архітектура високої доступності та масштабування системи Moodle
Балансування навантаження виступає першою точкою входу для клієнтських запитів і реалізується на базі зворотного проксі-сервера Nginx або HAProxy. Він розподіляє вхідний HTTP/HTTPS трафік між кластером ідентичних веб-серверів додатків. Обов’язковою умовою є активація механізму Sticky Sessions (Session Affinity), що закріплює сесію користувача за конкретним сервером, запобігаючи розривам авторизації під час переходів між сторінками. Відмовостійкість системи забезпечується відсутністю єдиної точки відмови: у разі виходу з ладу одного з веб-серверів, трафік миттєво перенаправляється на інші працездатні екземпляри. Спільний доступ серверів до файлів курсів (каталогу moodledata) організовано через мережеве сховище з використанням протоколу NFS (Network File System), що гарантує синхронність даних.
Кешування є критичним інфраструктурним компонентом для зниження навантаження на шар даних. Для системного кешування Moodle використовує вбудовану підсистему Moodle Universal Cache (MUC), яка у високонавантажених конфігураціях інтегрується із зовнішніми distributed-серверами Redis або Memcached. У Redis виноситься кеш сесій користувачів, метадані плагінів, мовні пакети та результати важких SQL-запитів, що дозволяє обробляти тисячі запитів на секунду за рахунок In-Memory розрахунків.
Масштабування шару даних реалізується через реплікацію реляційної бази даних PostgreSQL або MySQL за архітектурним патерном Master-Slave (Primary-Replica). Основний сервер (Master) приймає всі транзакції на запис та оновлення даних, а кілька Slave-серверів асинхронно реплікують ці зміни й обслуговують виключно запити на зчитування (Read-Only трафік). Розподіл запитів між Master та Slave вузлами здійснюється автоматично на рівні конфігурації підсистеми $DB Moodle або через проміжний пул з’єднань PgBouncer / ProxySQL, що суттєво розвантажує центральний сервер БД.
Контейнеризація та хмарна інфраструктура виступають сучасним технологічним стеком для керування цим кластером. Усі компоненти системи пакуються в ізольовані Docker-контейнери, а їх оркестрація здійснюється в хмарному середовищі Microsoft Azure за допомогою сервісу Azure Kubernetes Service (AKS) або Azure Container Instances. Використання хмарних рішень дозволяє налаштувати політики автоматичного горизонтального масштабування (Auto-scaling): у разі фіксації підвищення утилізації процесора на веб-вузлах під час іспитів, хмарна платформа автоматично розгортає нові контейнери з додатками, а після спаду активності – знищує їх, оптимізуючи використання ресурсів.

На відміну від застарілих версій, де інструменти інтеграції додавалися як сторонні локальні плагіни, у досліджуваній архітектурі базові інструменти управління ШІ-провайдерами винесені в окрему системну директорію public/ai/:

3.6.1 Аналіз підсистеми керування ШІ (AI API Controller)
Центральним архітектурним компонентом, який виступає єдиною точкою взаємодії з інтелектуальними сервісами, є клас manager, розташований у файлі public/ai/classes/manager.php. Він реалізує патерн проектування “Фасад” (Facade), інкапсулюючи внутрішню логіку перевірки ліцензій, вибору активних моделей та логування запитів у базу даних.
Для аналізу архітектурного принципу низької зв’язності (Low Coupling) та динамічного поліморфізму розглянемо метод process_action, який є точкою входу для обробки будь-яких ШІ-подій.
119     /**
120      * Process an action.
121      *
122      * This is the entry point for processing an action.
123      *
124      * @param base $action The action to process. Action must be configured.
125      * @return responses\response_base The result of the action.
126      */
127     public function process_action(base $action): responses\response_base {
128         // Get the action response_base name.
129         $actionname = $action::class;
130         $responseclassname = 'core_ai\\aiactions\\responses\\response_' . $action->get_basename();
131 
132         // Get the providers that support the action.
133         $providers = $this->get_providers_for_actions([$actionname], true);
134 
135         // Loop through the providers and process the action.
136         foreach ($providers[$actionname] as $provider) {
137             $result = $this->call_action_provider($provider, $action);
138 
139             // Store the result (success or failure).
140             $this->store_action_result($provider, $action, $result);
141 
142             // If the result is successful, return the result.
143             // No need to keep looping.
144             if ($result->get_success()) {
145                 return $result;
146             }
147         }
148 
149         // If we get here we've all available providers have failed.
150         // Return the result if we have one.
151         if (isset($result)) {
152             return $result;
153         }
154 
155         // Response if there are no providers available.
156         return new $responseclassname(
157             success: false,
158             errorcode: -1,
159             error: get_string('error:noproviders', 'core_ai'),
160             errormessage: get_string('error:defaultmessage', 'core_ai'));
161     }


Аналіз методу process_action показує чітке дотримання архітектурного принципу Polymorphism. Метод приймає абстрактний об’єкт дії base $action (це може бути як генерація тексту, так і розпізнавання зображень чи класифікація даних). Менеджер не знає специфіки конкретного ШІ-сервісу; він динамічно запитує перелік доступних провайдерів за допомогою внутрішнього виклику get_providers_for_actions. Наступний цикл реалізує відмовостійкість на рівні коду: якщо перший у списку провайдер (наприклад, OpenAI) повертає помилку, система не зупиняє роботу, а автоматично перенаправляє цей же об’єкт запиту до наступного налаштованого сервісу в циклі foreach.
Для забезпечення фінансового контролю, безпеки даних та моніторингу навантаження на систему, архітектура підсистеми вимагає обов’язкової фіксації кожної транзакції. Це реалізовано в приватному методі store_action_result, який інтегрує роботу з шаром збереження даних.
163     /**
164      * Store the action result.
165      *
166      * @param provider $provider The provider that processed the action.
167      * @param base $action The action that was processed.
168      * @param responses\response_base $response The result of the action.
169      * @return int The id of the stored action result.
170      */
171     private function store_action_result(
172         provider $provider,
173         base $action,
174         responses\response_base $response,
175     ): int {
176         global $DB;
177         // Store the action result.
178         $record = (object) [
179             'actionname' => $action->get_basename(),
180             'success' => $response->get_success(),
181             'userid' => $action->get_configuration('userid'),
182             'contextid' => $action->get_configuration('contextid'),
183             'provider' => $provider->get_name(),
184             'errorcode' => $response->get_errorcode(),
185             'error' => $response->get_error(),
186             'errormessage' => $response->get_errormessage(),
187             'timecreated' => $action->get_configuration('timecreated'),
188             'timecompleted' => $response->get_timecreated(),
189             'model' => $response->get_model_used(),
190         ];
191 
192         try {
193             // Do everything in a transaction.
194             $transaction = $DB->start_delegated_transaction();
195 
196             // Create the record for the action result.
197             $record->actionid = $action->store($response);
198             $recordid = $DB->insert_record('ai_action_register', $record);
199 
200             // Commit the transaction.
201             $transaction->allow_commit();
202         } catch (\Exception $e) {
203             // Rollback the transaction.
204             $transaction->rollback($e);
205             // Re throw the exception.
206             throw $e;
207         }
208 
209         return $recordid;
210     }
Даний фрагмент ілюструє застосування транзакційного проектування (start_delegated_transaction()). Запис даних у системний регістр ai_action_register захищено від збоїв: у разі виникнення виключення (\Exception $e) під час збереження відповіді від стороннього ШІ, транзакція повністю відкочується ($transaction->rollback($e)), що запобігає десинхронізації або появі “битих” записів у базі даних Moodle. Це повністю відповідає інфраструктурним вимогам надійності, що висуваються до інформаційних систем дистанційного навчання.


3.6.2 Аналіз точки входу REST API (REST Web Service Gateway)
Для забезпечення можливості інтеграції розроблених інтелектуальних сервісів із зовнішніми системами (мобільними додатками, сторонніми аналітичними платформами чи зовнішніми інтерфейсами), архітектура проєкту використовує уніфікований шлюз веб-служб REST. Головною точкою входу для обробки таких зовнішніх запитів є файл public/webservice/rest/server.php.
Даний компонент реалізує архітектурний патерн Front Controller, виступаючи єдиним шлюзом, який приймає всі REST-запити, ініціює процедуру автентифікації на основі перманентних токенів (Tokens Authentication), перевіряє стан протоколу в конфігурації системи та передає керування спеціалізованому обробнику сервера.

Детальний аналіз наведеної реалізації дозволяє виділити наступні архітектурні та безпекові рішення:
* Ізоляція середовища виконання та безпека виведення даних. Інструкція define('NO_DEBUG_DISPLAY', true); на самому початку файлу є критично важливою для забезпечення безпеки інформаційної системи. Вона пригнічує стандартне виведення системних помилок PHP та відладочних повідомлень ядра Moodle в тіло HTTP-відповіді. Це унеможливлює витік чутливих даних (таких як шляхи до файлів на сервері, структури таблиць БД або версії ПЗ) у разі виникнення критичних збоїв під час обробки AI-функцій зовнішніми користувачами.
* Контроль доступності інтерфейсів. За допомогою умовного розгалуження if (!webservice_protocol_is_enabled('rest')) система реалізує архітектурний принцип превентивного захисту. Якщо в адміністративній панелі платформи вимкнено REST-протокол, шлюз миттєво припиняє виконання (die), повертаючи стандартний HTTP-заголовок 403 Forbidden, що знижує навантаження на обчислювальні ресурси сервера при потенційних зловмисних скануваннях.
* Інкапсуляція логіки обробки та поліморфний запуск. Створення екземпляра класу new webservice_rest_server(...) з передачею константи методу автентифікації WEBSERVICE_AUTHMETHOD_ PERMANENT_TOKEN демонструє використання інкапсуляції високого рівня. Весь життєвий цикл обробки запиту (десеріалізація параметрів, перевірка прав доступу токена, виклик конкретної функції підсистеми ШІ та форматування результату в XML/JSON) приховано всередині методу $server->run();.
* Централізована обробка ранніх виключень. Функція raise_early_ws_exception(Exception $ex) відповідає за обробку виключень, що виникають на етапі ініціалізації системи (до повного завантаження ядра). Вона гарантує, що навіть у разі критичного збою клієнт отримає відповідь не у вигляді сирого тексту помилки сервера, а у валідному структурованому REST-форматі ($server->set_rest_format()), що є обов’язковою вимогою для стабільної роботи клієнтських веб-інтерфейсів та інтегрованих мікросервісів Data Science.


3.6.3 Методологічна довідка про використання інструментів штучного інтелекту
У ході виконання дослідження та підготовки текстових матеріалів роботи було використано сучасні інструменти генеративного штучного інтелекту. Відповідно до академічних стандартів, нижче наведено відомості про характер взаємодії з технологією:

119     /**
120      * Process an action.
121      *
122      * This is the entry point for processing an action.
123      *
124      * @param base $action The action to process. Action must be configured.
125      * @return responses\response_base The result of the action.
126      */
127     public function process_action(base $action): responses\response_base {
128         // Get the action response_base name.
129         $actionname = $action::class;
130         $responseclassname = 'core_ai\\aiactions\\responses\\response_' . $action->get_basename();
131 
132         // Get the providers that support the action.
133         $providers = $this->get_providers_for_actions([$actionname], true);
134 
135         // Loop through the providers and process the action.
136         foreach ($providers[$actionname] as $provider) {
137             $result = $this->call_action_provider($provider, $action);
138 
139             // Store the result (success or failure).
140             $this->store_action_result($provider, $action, $result);
141 
142             // If the result is successful, return the result.
143             // No need to keep looping.
144             if ($result->get_success()) {
145                 return $result;
146             }
147         }
148 
149         // If we get here we've all available providers have failed.
150         // Return the result if we have one.
151         if (isset($result)) {
152             return $result;
153         }
154 
155         // Response if there are no providers available.
156         return new $responseclassname(
157             success: false,
158             errorcode: -1,
159             error: get_string('error:noproviders', 'core_ai'),
160             errormessage: get_string('error:defaultmessage', 'core_ai'));
161     }


163     /**
164      * Store the action result.
165      *
166      * @param provider $provider The provider that processed the action.
167      * @param base $action The action that was processed.
168      * @param responses\response_base $response The result of the action.
169      * @return int The id of the stored action result.
170      */
171     private function store_action_result(
172         provider $provider,
173         base $action,
174         responses\response_base $response,
175     ): int {
176         global $DB;
177         // Store the action result.
178         $record = (object) [
179             'actionname' => $action->get_basename(),
180             'success' => $response->get_success(),
181             'userid' => $action->get_configuration('userid'),
182             'contextid' => $action->get_configuration('contextid'),
183             'provider' => $provider->get_name(),
184             'errorcode' => $response->get_errorcode(),
185             'error' => $response->get_error(),
186             'errormessage' => $response->get_errormessage(),
187             'timecreated' => $action->get_configuration('timecreated'),
188             'timecompleted' => $response->get_timecreated(),
189             'model' => $response->get_model_used(),
190         ];
191 
192         try {
193             // Do everything in a transaction.
194             $transaction = $DB->start_delegated_transaction();
195 
196             // Create the record for the action result.
197             $record->actionid = $action->store($response);
198             $recordid = $DB->insert_record('ai_action_register', $record);
199 
200             // Commit the transaction.
201             $transaction->allow_commit();
202         } catch (\Exception $e) {
203             // Rollback the transaction.
204             $transaction->rollback($e);
205             // Re throw the exception.
206             throw $e;
207         }
208 
209         return $recordid;
210     }
